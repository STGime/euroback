## Postgres roles
- `eurobase_gateway` — runtime role used by the gateway + worker pods for **SDK runtime traffic** (`/v1/*`). DML only on `public.*`, USAGE + CREATE on tenant schemas so the SDK DDL endpoint works. NO DDL on `public.*`. Wired via `DATABASE_URL` in the `eurobase-secrets` k8s Secret.
- `eurobase_developer` — runtime role used by the gateway pod for **platform-authenticated developer traffic** (console + MCP under `/platform/*`). Member of `eurobase_migrator` with INHERIT, so it gets ownership-equivalent privileges. Each platform tx runs `SET LOCAL ROLE eurobase_migrator`, so DDL/REFERENCES against migrator-owned tables works and any newly created objects are owned by the migrator (uniform with CI-applied migrations). Wired via `DATABASE_URL_DEVELOPER` in the same Secret. **Two distinct DB pools share one process by design** — runtime exploit ≠ elevated privileges.
- `eurobase_migrator` — deploy-only role. Owns `public.*` tables and tenant schemas; runs migrations via the `migrate` Kubernetes Job in CI. Wired via `DATABASE_URL_MIGRATOR` in the same Secret.
- `eurobase_function_runner` — runtime role used by the **edge functions runner pod** (deploy/k8s/functions.yaml). NO direct grants on any tenant schema or `public.*` (beyond USAGE + helper-function EXECUTE; it loads function code only via `runner_get_function` (000125) and vault secrets via `vault_get_for_runner` — `000126` removed its historic table grants and fails loud if any remain). **Gets no new tenant-role memberships** since `000127` (stage B phase 1b), and customer SQL never runs on this login — it runs on a separate connection that logs in as the tenant's own `<schema>_func` role (see *Per-tenant function logins*). **On prod the pre-000127 memberships remain** until Scaleway support runs `scripts/ops/runner-membership-revoke.sql`: they are recorded with grantor `_rdb_superadmin`, which migrator cannot revoke. `scripts/ops/check-migration-bootstrap.sh` prints how many remain (target 0). Wired via `DATABASE_URL_FUNCTION_RUNNER` in the same Secret. Per-tenant `<schema>_func` roles are created by `provision_tenant` (migration `000047`).
- `<schema>_ddl` — **per-tenant** runtime role for **tenant schema migrations** (`POST /platform/projects/{id}/migrations`, #190). NOLOGIN until use; CREATE on its own schema only, USAGE + helper EXECUTE on `public`, NO `public.*` table grants, **member of nothing**. Owns the tenant's application tables. Created by `provision_tenant` (migration `000063`). To run a migration, the gateway (via the developer pool, as migrator) sets the role's LOGIN password (`ALTER ROLE … PASSWORD`, derived `HMAC-SHA256(DDL_PASSWORD_SECRET, schema)`), then opens a short-lived connection **as that role** and runs the SQL. Because the connecting role is a member of exactly one tenant, a malicious migration body that does `RESET ROLE` lands back on the same role and **cannot pivot into another tenant** (a shared login role member of all tenants would be — that was the #209 review finding). Bookkeeping is via two `session_user`-bound SECURITY DEFINER helpers (`record_tenant_migration` / `tenant_migration_checksum`), so a tenant role has no direct grant on `public.tenant_migrations` and can neither forge nor read other projects' history. Requires `DDL_PASSWORD_SECRET` (≥32 bytes) in `eurobase-secrets`; if unset, the endpoint fails closed (503). **Two Scaleway-owned-object grants `eurobase_migrator` needs** (both because the `eurobase` DB and schema `public` are owned by `_rdb_superadmin` / `pg_database_owner`, not the customer — a grant attempted as a non-owner is a silent WARNING-not-error no-op): **(1) DB CONNECT** — `eurobase_migrator` must own the `eurobase` database or hold `CONNECT … WITH GRANT OPTION`, so it can grant CONNECT to the per-tenant roles; **(2) schema-public USAGE** — `eurobase_migrator` must hold `USAGE ON SCHEMA public … WITH GRANT OPTION`, so it can grant USAGE to the `_ddl` roles. The `_ddl` role needs USAGE on `public` because the apply path makes *ad-hoc, parse-time* `public.*` references (the `tenant_migration_checksum` / `record_tenant_migration` bookkeeping calls, and `CREATE POLICY … public.is_service_role()` in migration bodies) — EXECUTE on those functions is not enough, schema USAGE is checked at name-resolution time. Both grants are obtained once from Scaleway support (as `_rdb_superadmin`); the apply path then re-grants **and verifies** each per-tenant role's CONNECT (`has_database_privilege`) and public USAGE (`has_schema_privilege`) on every `migrations up`, failing loud if either can't be granted. (Note: func roles do **not** need public USAGE — RLS policies are OID-resolved, so policy evaluation checks only EXECUTE, which `provision_tenant` grants.) Reproducible isolation proof: `scripts/verify-tenant-migration-isolation.sh`.
- **CONVENTION — gateway pool CANNOT read `organizations` / `org_members` / `support_requests` / `contact_requests`:** migration 000114 REVOKEs SELECT on the two org tables from `eurobase_gateway` (org membership is Team-tier platform config, NOT SDK-facing so runtime SQLi cannot exfiltrate rosters or OIDC configs); migration 000112 does the same for `contact_requests`; migration 000115 does the same for `support_requests`. Any query that joins or reads these tables MUST run on the developer pool (`NewTenantService(developerPool, ...)`, or an `OrgsForSSO`-style adapter in the auth package). The mistake was made three times back-to-back (#538 hotfix on `ListProjects` UNION, then #545/#546 on `lookupPlatformUserForSSO`); the failure signature is always the same: prod 500 with `SQLSTATE 42501 permission denied for table <name>`. The fix pattern is always the same: split the query so the gateway-pool side touches ONLY `platform_users` (which the gateway CAN read via a per-column grant on `email` / `is_superadmin` / `id`) and let the developer-pool answer membership questions.
- **Lockdown (migration `000064`, #217):** `provision_tenant_ddl_role(text)` was created with a NULL ACL (default `EXECUTE → PUBLIC`); once a per-tenant role has USAGE on `public` that becomes a cross-tenant footgun (a migration body / edge-function SQL could call this migrator-owned SECURITY DEFINER function), so `000064` does `REVOKE EXECUTE … FROM PUBLIC` on it (it's only ever called in migrator context, so no re-grant is needed). A #217 sweep confirmed it was the only PUBLIC-executable privileged secdef function in `public` *on prod*; a later fresh-DB sweep found three more that only prod had locked down by hand (`provision_tenant`, `deprovision_tenant`, `ensure_data_access_log_partition`), fixed by `000126`. **CONVENTION — recurrence prevention:** every **new** `SECURITY DEFINER` / helper function created by migrator in schema `public` MUST `REVOKE EXECUTE … FROM PUBLIC` (or `GRANT EXECUTE` only to the roles that need it — `eurobase_gateway` / `eurobase_function_runner` / per-tenant roles) **in its own migration**. The obvious blanket guard (`ALTER DEFAULT PRIVILEGES FOR ROLE eurobase_migrator IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`) was tested against PG 16 and is a **no-op** (it does not suppress PUBLIC EXECUTE for a non-bootstrap owner role), so do not rely on it — the per-function REVOKE is the rule. `scripts/verify-tenant-migration-isolation.sh` check 11 asserts the lock holds.
- **`pg_stat_activity` is role-scoped, not schema-scoped — and every SDK tenant shares `eurobase_gateway`** (security report 2026-09-16). PostgreSQL shows the full `query` text of *same-role* backends to any session of that role with **no extra grant** — `pg_read_all_stats` is irrelevant (never granted, and same-role visibility doesn't depend on it). So one tenant could read every other tenant's in-flight SQL (incl. inlined literals) plus the control plane's own statements via `SELECT query FROM pg_stat_activity` on `/v1/db/sql`; the **platform SQL path leaks identically**, because `eurobase_developer` → member of `eurobase_migrator` → member of `eurobase_gateway` (000045) gives it the gateway's session visibility even without `SET ROLE`. Root cause: the cross-schema scanner is dot-keyed and never examines a bare `pg_stat_activity`, which resolves via the always-implicit `pg_catalog` search path (cannot be removed by `SET LOCAL search_path`). The underlying function `pg_stat_get_activity()` returns the same data, so a view-only block is insufficient. **Primary control (deployable):** `query.ValidateNoCatalogRefs` refuses any `pg_`-prefixed identifier — bare or qualified, view or function — on the SDK **and** platform SQL/transaction paths, with a tiny allowlist (`pg_temp`, `pg_typeof`, `pg_get_serial_sequence`, `pg_size_pretty`, `pg_column_size`, `pg_backend_pid`). **DB-level belt (needs Scaleway support, as `_rdb_superadmin`):** `REVOKE SELECT ON pg_catalog.pg_stat_activity FROM PUBLIC; REVOKE EXECUTE ON FUNCTION pg_catalog.pg_stat_get_activity(integer) FROM PUBLIC;` (re-grant to a dedicated monitoring role if ops need it) — verified on PG16 to deny all three access forms while leaving `pg_backend_pid()` working; `scripts/verify-tenant-migration-isolation.sh` check 12 asserts it. Do **not** put that REVOKE in a migration: as `eurobase_migrator` it is the same silent-no-op trap as the other Scaleway-owned-object grants. **Known residual — the REVOKE is the real control, not a belt:** parse-time scanning is complete only for *direct* reads. The scanner deliberately skips dollar-/single-quoted regions, so any surface that can define an executable body — the platform SQL and transaction endpoints (`CREATE FUNCTION … $$ SELECT query FROM pg_stat_activity $$`, `DO $$ … $$`) and the tenant migrations endpoint (its validator likewise blanks dollar-quoted bodies) — can smuggle the read into a body, and `SELECT * FROM peek()` carries no `pg_` token. A migration-planted function can then be invoked from the SELECT-only **SDK** path, which runs as gateway. Dynamic SQL (`EXECUTE format('pg_' || 'stat_activity')`) evades *any* lexical scan, so extending the scanner into bodies would stop copy-paste, not intent. Until the superuser REVOKE lands, treat the cross-tenant read as **open for any customer who can reach a body-defining endpoint**; the Scaleway ticket is therefore required, not optional.

The migration files only do GRANT / REVOKE / membership. (Per-tenant `<schema>_func` and `<schema>_ddl` roles are NOLOGIN and created by `provision_tenant`, not the console.)

## Functions runner HMAC
- Gateway → runner traffic is HMAC-SHA256-signed using `FUNCTIONS_RUNNER_HMAC_SECRET` (≥32 bytes) shared via the `eurobase-secrets` k8s Secret. Both gateway and functions Deployments read it via `envFrom: secretRef: eurobase-secrets`.
- Generate via `openssl rand -hex 32`. Rotate by setting a new value and rolling both Deployments together.
- Runner enforcement is controlled by `FUNCTIONS_RUNNER_HMAC_REQUIRE_SIGNED`:
  - `true` → strict; missing or invalid signature → 401.
  - unset/other → soft mode (warn-only on missing); invalid signature still 401. Use during rollout window.
- Gateway aborts startup if the secret is missing in production (`ENV=production` or `DOMAIN_SUFFIX` ends with `eurobase.app`).

## Console passkey MFA (#621)
- WebAuthn relying party defaults to the `CONSOLE_URL` host (`console.eurobase.app` in prod) — deliberately **not** `eurobase.app`, which tenant apps share. `WEBAUTHN_RP_ID` / `WEBAUTHN_RP_ORIGINS` (comma-separated) override. Changing the RP id orphans every enrolled passkey — treat it as permanent.
- ≥ 1 row in `platform_passkey_credentials` = MFA on for that user: `SignIn` returns `mfa_required` + a single-use step-up token instead of a session. Passkey sessions mint `login_via=passkey`, which `sso_required` orgs refuse (only `sso` for the matching org passes).
- Both passkey tables (migration `000123`) are REVOKEd from `eurobase_gateway` — all passkey queries run on the developer pool. The gateway **aborts startup** if the developer pool is set but WebAuthn setup fails (running without passkeys would let MFA accounts sign in with the password alone).
- Username-less login `begin` is **stateless** (HMAC-signed challenge token keyed off the platform JWT secret; single use recorded at finish) and deliberately not rate-limited — per-IP limits are product-wide behind the LB.
- Password reset clears all passkeys (same tx as the password update, developer pool) + sends a notice email (MVP recovery, accepted trade-off). Follow-ups: #628 (org "require MFA"), #629 (IdP-MFA verification for SSO), #630 (end-user passkeys).

## Per-tenant function logins (stage B phase 1a + 1b)
- `FUNC_PASSWORD_SECRET` (≥32 bytes, `openssl rand -hex 32`) in `eurobase-secrets` — read by the **worker** and the **functions runner**. Derives each shared-cluster tenant's `<schema>_func` login password: `HMAC-SHA256(secret, "funcpw:"+schema)`, hex (`internal/tenantlogin`, mirrored in `functions-runner/tenant_db.ts`; a pinned test vector keeps them in sync).
- Worker (`tenantlogin.Ensurer`, startup + every 5 min, developer pool as migrator): `ALTER ROLE <schema>_func LOGIN CONNECTION LIMIT 8 PASSWORD …` + `RESET ALL` (role-wide and `IN DATABASE`) + `GRANT CONNECT`, verified with `has_database_privilege`.
- Cron: `sql` / `rpc` schedules run the same way — the worker opens a short-lived connection **as `<schema>_func`** per job (`cron.Executor.WithTenantLogins`), never on its shared pool; without the secret those jobs fail. RLS identity per job via `cron_jobs.run_as` (#643, migration `000128`): `service` sets `app.end_user_role='service'` in the job's tx (like a user-less edge function; default for new jobs), `none` sets nothing (all jobs that existed before 000128). The console's Test Run calls `POST /platform/projects/{id}/cron/test` (#645): `cron.Executor.DryRun` — same validation, tenant login and `run_as` as the scheduled run, always rolled back (the gateway builds it from its own `DATABASE_URL` config + `FUNC_PASSWORD_SECRET`; 503 without). The statement is also checked on save and before each run with the SQL endpoints' validators plus `query.ValidateNoRoutineOrSessionObjects` (no DO / CREATE FUNCTION|PROCEDURE / temp objects / `set_config`, mirroring the runner guard).
- Gateway: `CreateProject` applies the new tenant's login right after `provision_tenant` commits (best effort; the worker's pass catches up).
- Runner: `ctx.db.sql` runs **only** on a connection that **logs in as `<schema>_func`** (1 per tenant per pod, per-pod cap `RUNNER_TENANT_CONN_CAP`=10, 30 s idle, LRU; **connection budget**: a rollout at HPA max runs 5 pods (4 + default 25% surge) × (10 tenant + 3 shared) = 65, + ~25 gateway/worker ≈ 90 of `max_connections`=100 (3 reserved), and `FuncConnLimit`=8 ≥ max pods + 1 surge + 1 cron job connection + 1 console dry run; the gateway allows at most 2 dry runs at once per pod (1 per project), 429 beyond — change these together, see `deploy/k8s/functions.yaml`). Its own login is used only for `runner_get_function` / `vault_get_for_runner`. **No shared-connection fallback (phase 1b):** a fallback is a path a tenant can steer into (e.g. invoke during the gap before its login exists), and on the shared login a planted plpgsql function doing `EXECUTE 'SET ROLE <other>_func'` reached every tenant. A failed login returns a retryable error to the function instead. A tenant can change its own `_func` password from function SQL (Postgres allows it), which locks it out of its own DB until the worker's next full pass (`FullPassInterval`, 15 min) **and — while the prod RDB endpoint is public (ACL `0.0.0.0/0`, found 2026-09-25) — gives it a direct session as its own role**: still no cross-tenant access, but outside the runner's statement guard/timeout. The Ensurer therefore sets `CONNECTION LIMIT 8` (`FuncConnLimit`; a role cannot raise its own) and `RESET ALL` on every pass. Real fix: move the RDB to the cluster's private network and close the public ACL (tracked separately). **CONVENTION:** never reintroduce a shared login that is a member of tenant roles, and never run customer SQL on the runner's own connection.
- Set in prod (2026-09-25) with `./scripts/ops/set-func-password-secret.sh` (generates the value without printing it, patches `eurobase-secrets`, restarts worker then functions). **Required** since phase 1b: without it `ctx.db.sql` fails. Too short = worker refuses to start. Rotation: set the new secret on worker, gateway and functions together, then restart the worker first; function SQL fails with a retryable login error until the worker has re-applied the passwords (seconds after its startup pass).

## Connection pooling prerequisites (#641)
- Plan: PgBouncer (transaction mode) in front of the shared cluster — Notion "Plan: Connection pooling for the platform database (#641)".
- **Two poolers (#651, #653):** `pgbouncer` (`deploy/k8s/pgbouncer.yaml`) is the **runner's** — tenant roles only, and **no secrets at all in the pod** (it's reachable from tenant function code): the **worker** derives each tenant's SCRAM verifier (it holds `FUNC_PASSWORD_SECRET` anyway) and publishes them plus the upstream `host:port/db` every 15 s to the Secret `pgbouncer-tenant-userlist` (`PGB_USERLIST_SECRET`; RBAC in `deploy/k8s/pgbouncer-userlist-rbac.yaml`: worker SA may get/patch that one Secret, the pooler SA may only get it; the Secret is declared without data so `kubectl apply` never clobbers it). The pooler (`PGB_TENANT_SOURCE=k8s-secret:…`) reads it with a projected service-account token mounted only into its `render`/`userlist` containers (not `pgbouncer`); a compromised pooler gets no master secret and no platform password — only the verifiers and (inherent to SCRAM pass-through) the ClientKey of tenants that connect *during* the compromise, so the incident response is: **rotate `FUNC_PASSWORD_SECRET`** (worker re-applies all logins, publisher republishes). The publisher writes on its first pass (even with zero tenants), on change, and every 5 min (heals a wiped Secret); a new tenant is poolable within ~15 s (5 s publish + 10 s sync) — until then the runner returns its retryable login error. The upstream address is read at pooler init (a DB host change needs a pooler roll). Kubernetes caps a Secret at 1 MiB (~6k tenants) — revisit then. The worker can get/patch but not create the Secret: if it's deleted, re-apply `pgbouncer-userlist-rbac.yaml`. `pgbouncer_userlist_published_age_seconds` + alert `PgBouncerUserlistStale` catch a stopped publisher. CI: the worker's image is set (after migrations) and its first publish awaited in "Deploy to Kapsule", then the poolers roll, then the other services — `kubectl apply` of `worker.yaml` never changes its image (pinned by `set image`). Its init container waits for a first publish (upstream key present; an empty list = no tenants) and CI rolls the worker and waits for that before rolling the pooler. `pgbouncer-userlist publish` does the worker's job for tests (`file:` store). Ingress from functions only. The stats user can see tenant role names (`SHOW POOLS/USERS`); `/metrics` must stay per-alias — never add a `user` label. `pgbouncer-gateway` (`deploy/k8s/pgbouncer-gateway.yaml`) is the **gateway's** — platform roles only (`PGB_INCLUDE_TENANTS=0`), ingress from the gateway only, and the functions egress policy (`app: pgbouncer`) can't reach it; unused until PR 4. Both sidecars expose `/metrics` on :9127 (stats-only admin user with a random per-pod password; per-alias labels): `pgbouncer_up`, `pgbouncer_clients_waiting`, `pgbouncer_maxwait_seconds`, `pgbouncer_client_connections` / `pgbouncer_max_client_conn`, servers active/idle — scraped by Alloy; alert rules in `deploy/k8s/cockpit/alerts.yaml` group `eurobase-pgbouncer` (import into Cockpit by hand, like the gateway rules). **Alloy is not deployed in prod yet (2026-09-25)** — none of the Cockpit alerts (gateway or pooler) fire until `deploy/k8s/cockpit/alloy.yaml` is applied per its README; its relabel keeps only container ports named `metrics` (otherwise app/pooler ports and init containers are scraped, blocked by NetworkPolicy, and report `up=0` forever). `scripts/test-pgbouncer.sh` also runs both prod modes (`TestPoolerSplit`); `scripts/ops/pgbouncer-smoke.sh` checks the gateway via its pooler, a tenant via the runner's, and that the runner's refuses the gateway role.
- **Runner via PgBouncer (PR 3):** the functions runner's tenant connections (`ctx.db.sql`) use `FUNC_DB_POOLER_URL` (`pgbouncer…:6432/eurobase_tenant`) — the tenant alias with its own server-connection cap (`PGB_TENANT_MAX_DB_CONNECTIONS` 15/replica), separate from the platform alias (10/replica), so busy tenants can't take platform connections. The runner's own platform lookups stay direct. Per tenant: 2 replicas × pool 2 + cron + dry run = 6 ≤ `FuncConnLimit` 8 (a runner rollout can briefly add old pods' direct connections). Runner HPA max 6; `RUNNER_TENANT_CONN_CAP` counts client connections to the pooler (default 30 with the pooler). postgres.js **3.4.7** (3.4.4 left a query hanging forever and threw an internal error when PgBouncer closed a waiting client); PgBouncer errors: auth failures arrive as `08P01 … authentication failed` (`isLoginError`), a full tenant pool / no client slots as `08P01 query_wait_timeout` / `no more connections allowed` (`isPoolerBusyError` → retryable "database is busy"). The runner has a global `unhandledrejection` guard (postgres.js may emit a connection error as an unhandled rejection besides rejecting the query) so one tenant's broken connection can't crash the process. The image build asserts PgBouncer ≥ 1.23 (`[users] pool_size` needs it). The developer role is only included with `PGB_INCLUDE_DEVELOPER=1`.
- **No session state between requests:** every pool whose queries touch tenant tables resets each connection on release — that runs tenant-defined code (RLS policy expressions and the functions they call, triggers, defaults), not only customer-supplied SQL. `db.ResetSession` is a pgxpool `AfterRelease` hook (pgx runs it in a goroutine, off the request path): `DISCARD ALL`, plus `DeallocateAll` when the exec mode caches statements; a failed reset destroys the connection. Installed via `db.NewPool(…, db.WithSessionReset())` on the gateway's runtime + developer pools and the worker's pools (exports), and on Team `PoolCache` pools. **Any new pool that touches tenant tables must use it.** The query engine's `releaseClean` resets synchronously only for pools without the hook (tests, tools). River's LISTEN is on a hijacked connection, unaffected. The functions runner's per-tenant clients (1 connection per tenant) are *not* reset between invocations of the same tenant — not cross-tenant; parser agreement is pinned per transaction. **This does not cover a transaction-mode pooler**: after COMMIT the reset may reach a different server connection — the PgBouncer PR needs its own (`server_reset_query_always = 1` or an in-transaction reset before COMMIT).
- **Parser-agreement rule:** the lexical guards (Go `privilege_guard.go`, runner `sql_guard.ts`) refuse `standard_conforming_strings`, `backslash_quote` and `escape_string_warning` anywhere — they change how the server tokenizes string literals, so a guard and the server could read the same text differently. Customer statements run over the extended protocol (`execCustomerStatement` / cron `execExtended`), so the server itself refuses a second statement, and each is preceded by `SET LOCAL standard_conforming_strings = on` (engine and runner), so the server tokenizes the way the guards do even if earlier customer code in the transaction changed it.
- **Must stay on direct (non-pooled) connections** once a pooler exists: golang-migrate (`DATABASE_URL_MIGRATOR`; session advisory lock, multi-statement files), tenant `_ddl` migration connections (a pooled server connection would outlive the demotion back to NOLOGIN), the worker's River client (`LISTEN`), and the export's `pg_dump` (#656: session-level `SET`s and an imported snapshot — if the developer pool moves behind the pooler, give `libpqEnv` the direct URL).
- `query.HasMultipleStatements` uses the shared tokenizer (`scanIdentifiersAndDots`), so it reads `E'…'` / `U&"…"` / dollar quotes the same way as the other guards. Where the server must enforce a single statement, use `PgConn.ExecParams` — pgx `Exec` without arguments uses the simple protocol, which runs every statement.

## Team-tier routing (epic #684)
- A project with a live `project_databases` row is served from its dedicated instance **or refused — never from the shared cluster** (no schema there for a project created as Team; only a stale copy for one upgraded from Pro, where a fallback silently reads/writes the wrong database). `tenant.PlatformTenantContext` answers 503 when such a project's owner pool can't be opened (#678; incl. the `provisioning` window, before the row has a host); console engines route with `query.TenantPoolFromContext`. Exception: project settings (`PATCH /v1/tenants/{id}`, platform tables) use `PlatformTenantContextForSettings`, which continues without the pool — the one step needing the dedicated DB, the OAuth-secret vault write, refuses on its own (`VaultService.tenantPool` → `query.ErrDedicatedPoolUnavailable`, 503) instead of using the shared vault. The vault refuses whenever the request's `ProjectContext` says the project has a dedicated DB and no pool is on it — so with `TEAM_TIER_ROUTING` off, a Team project's SDK vault calls (incl. OAuth sign-in) are refused, not served from shared. Vault handlers map the refusal to 503 (`writeDedicatedUnavailable`). Note: `pgxpool` connects lazily, so an *unreachable* dedicated host yields a pool and a later handler error (500), never the shared cluster; the 503 covers no cipher, bad credentials/DSN, and a row still provisioning with no host.
- **SDK (#680):** `sdkTenantPoolMw` (on `/v1/db`, `/v1/auth`, `/v1/vault`, `/v1/storage`, OAuth callbacks — always after `MaintenanceModeMiddleware`) puts a Team project's **runtime** pool (never the owner — SDK traffic must stay under RLS) on the request, or answers **503** — no shared fallback, including with `TEAM_TIER_ROUTING` off or no cipher. `StorageHandler.tenantPool` refuses (`ErrDedicatedPoolUnavailable`) for a dedicated project without a pool; storage metadata (`storage_objects`) and the ownership check (`assertObjectVisible`) go to that pool, `export_requests` stays on the platform DB; upload resolves the pool before the S3 PUT. Console storage: `PlatformStorageContext` puts the dedicated owner pool on the request or answers 503, like `PlatformTenantContext`. The harness runs Garage (EU S3 server, `dxflrs/garage`) for the storage checks — MinIO no longer publishes community images to Docker Hub.
- **Background jobs (#681):** the gateway's hourly token cleanup cleans a Team project's `refresh_tokens` / `email_tokens` on its dedicated database through a short-lived owner pool (`dbprovider.OpenOwnerPool`, never `PoolCache`), and skips the project (warning) when that database can't be opened — it never falls back to the shared cluster. Any new per-tenant background job must do the same.
- **Schema / DDL (#679):** every tenant-schema DDL, validation and catalog listing in `internal/query` (`ddl.go`, introspection, index list, RLS audit, schema-change backfill) resolves its pool with `tenantDDLPool`: the dedicated pool on the request, else `ErrDedicatedPoolUnavailable` when `query.WithDedicatedDB` marks the project as Team, else the shared pool. Platform tables (`projects`, `schema_changes`) stay on the shared `pool` argument — never read them through the tenant pool. `/schema`, `/schema/changes`, `/schema/rls-audit` are behind `PlatformTenantContext`. SDK DDL (`sdkDDLAdapter`) runs a Team project's DDL on its dedicated **owner** pool (the counterpart of shared-cluster `eurobase_migrator`), or 503 (routing off / pool unavailable).
- **Instance size and connection budget (#682):** every Team / Legal-Team project gets `dbprovider.DefaultTeamSize` (small = Scaleway `db-dev-s`, **2 vCPU / 2 GB RAM** per the Scaleway API on 2026-09-26; `db-gp-s` is 8 vCPU / 32 GB) — on create, upgrade and retry alike. Scaleway's PostgreSQL `max_connections` default is **100** on every version and node type (range 50–10000, not hot-configurable); we keep it. Budget per instance: gateway `PoolCache` runtime 8 + owner 8 per pod (1 replica; ×2 during a rollout = 32), a tenant export 2 (owner pool + pg_dump; a user export can run concurrently), token cleanup / bootstrap ~1 each, plus the worker's own rollout overlap → **≈40 platform worst case**; Postgres reserves `superuser_reserved_connections` (3) and Scaleway's agents take a few more, so ~95 are usable. `eurobase_readonly` has `CONNECTION LIMIT` `dbprovider.ReadonlyConnLimit` (10, set by `BootstrapDedicated`; instances bootstrapped before #682 — none in prod — need it set by hand; the owner can lift it, so it protects customers from themselves, not a security boundary); the rest is the customer's owner URL (full-DB product decision: it is uncapped — a PG16 owner can't limit itself — so a customer exhausting it only hurts their own project; console docs chapter 25 gives ORM pool sizes). Grow `PoolCache`'s per-project pools or the gateway replicas → update this budget and the docs. Pooler in front: #485.
- `scripts/test-team.sh` → `TestTeamEndToEnd` (CI: `team-e2e.yml`) drives the real router for a fresh and an upgraded Team project (stale shared copy with a decoy row). Open gaps are in `teamKnownGaps` with their expected error; **a fix PR must remove its entry** (the test fails once a gap passes), and a PR routing a new surface should add a check.

## Team-tier runtime password (M2.5 part 2b)
- `RUNTIME_PASSWORD_SECRET` (≥32 bytes) in `eurobase-secrets` derives the deterministic `eurobase_gateway` login password on each dedicated managed-PG instance: `HMAC-SHA256(secret, project_database_id)`, hex64. Same pattern as `DDL_PASSWORD_SECRET`. Deterministic derivation is what lets concurrent runners (provision retry + backfill sweeper) set the same live Scaleway password so the persisted ciphertext in `project_databases.runtime_*` can't diverge from what Scaleway holds. Generate via `openssl rand -hex 32`.
- Empty is legal (dev) — worker skips the bootstrap step and leaves `runtime_username` NULL; SDK routing falls back to shared cluster. Too-short (< 32 bytes) fails worker startup rather than silently deriving from a weak HMAC key.

## Mollie billing
- Payment processor is Mollie (Dutch, EU-headquartered — already in `sub_processors` from migration `000025`).
- API-key secrets in `eurobase-secrets`: `MOLLIE_API_KEY_TEST` (starts `test_`), `MOLLIE_API_KEY_LIVE` (starts `live_`), `MOLLIE_ENV` (`test`|`live`). The client's `NewClient` construction logs a warning if the API-key prefix doesn't match the env, so ops key mixups are visible in the first minute after deploy.
- **Test key first, live key on the flip.** Staging always runs `MOLLIE_ENV=test`; prod runs `MOLLIE_ENV=test` until PR 8 lands and `BILLING_ENABLED=true`, then flips to `live`.
- Empty API key is legal — client construction succeeds and every endpoint returns `ErrUnauthorized` without hitting the network. Lets dev environments boot without secrets.
- Feature flag: `BILLING_ENABLED` (default false in prod, true in staging). All billing HTTP handlers return 503 when false (not 404 — the route is registered so 503 is a clearer signal of "temporarily off" than "doesn't exist").
- URL config: `CONSOLE_BASE_URL` (post-checkout redirect target, default `https://console.eurobase.app`), `PLATFORM_BASE_URL` (webhook URL Mollie POSTs to, default `https://api.eurobase.app`).
- **Estonian VAT status:** Eurobase OÜ is below the €40k VAT threshold, so invoices carry "Not VAT-registered under Estonian VAT Act §19" and no VAT is charged. Register for VAT and switch to reverse-charge B2B / local-VAT B2C on crossing the threshold.
- **Recurring flow.** Mollie doesn't create a subscription until a mandate exists. Checkout (PR 3) creates a first Payment with `sequenceType=first`; the user completes it on Mollie's page; the webhook (PR 4) sees `paid` + `mandateId`, then creates the recurring Subscription against the mandate.

## Compliance exports (#654)
- Exports (`compliance.WriteTenantExport` / `WriteUserExport`) read tenant tables through `compliance.ExportSource`: the worker's developer pool as `eurobase_developer` itself (**no** `SET ROLE`), which owns the tables legacy MCP DDL created and via INHERIT has the privileges of every other tenant-table owner (`eurobase_migrator`: platform + SQL-editor tables; `<schema>_ddl`; `eurobase_gateway`: legacy SDK DDL) — `SET ROLE eurobase_migrator` would lose the developer-owned ones — in one `REPEATABLE READ READ ONLY` snapshot with **`row_security = off`** and **`restrict_nonsystem_relation_kind = 'view, foreign-table'`** (only tables and sequences are ever read with the export login's privileges; a view or foreign table under a name the export reads is refused, not evaluated — needs PG ≥ 16.4, like pg_dump). Owners bypass RLS, and `row_security = off` makes any read RLS would still limit (FORCE RLS, a foreign owner) **raise an error instead of returning fewer rows**. **CONVENTION:** never read export data through a runtime role — that silently dropped every table with end-user RLS (user_identities, owner-only tables) until #654.
- Tables are listed from `pg_catalog`, not `information_schema` (privilege-filtered). Every table gets a file (empty ones too) and an entry in `_metadata.json` `tables` (rows, `exported` / `truncated` / `failed` + reason); `complete` / `warnings` go into `_metadata.json` and `export_requests` (000129) and are shown in the console. Credential columns of the system tables (`query.SensitiveSystemColumns`: `password_hash`, `token_hash`, vault `secret` / `nonce`) are redacted and listed as `redacted_columns`.
- **Archives in the storage browser (#655):** the worker writes archives straight to the project bucket under `exports/<project-id>/` — no `storage_objects` row; `export_requests` is their record. The storage handler treats that prefix as platform-managed: download / download URL only for console callers with **admin** (the compliance export API's bar, not storage's viewer) and only for a completed, unexpired `export_requests` row of the project; upload / upload URL / delete refused (403) for every caller; listing hides it from anyone who can't download it. **Edge functions** (`functions.InternalStorageHandler`) are refused every operation there, download URLs included — a function that signs a request-supplied key would otherwise hand the dump to end users. The console's folder delete / rename skip archives; `cmd/backfill-storage` neither tracks nor renames them. The worker and the expiry cleanup write S3 directly, not through a handler. The namespace is `storage.ExportArchivePrefix(projectID)`; build archive keys from it.
- **Schema section (#656), tenant exports only, `format_version` 2:** `schema/schema.sql` is `pg_dump --schema-only --no-owner --no-privileges --strict-names --schema=<tenant>` run by the worker as the export source's own login (settings from the source pool via `libpqEnv`: host, user, password, `sslmode`/`sslrootcert` — nothing else from the worker env), importing the export transaction's snapshot (`pg_export_snapshot()` from the **top-level** tx, before any savepoint — it refuses a subtransaction), so DDL and rows match. The worker image installs `postgresql16-client` (build asserts ≥ 16; `pg_dump` must be ≥ the server's major — bump it with the RDB engine). Also `schema/sequences.json` (last_value / is_called), `schema/auth_manifest.json` (`projects.auth_config` minus secret-looking keys — listed in `redacted_keys` — plus `email_templates`), `schema/storage_manifest.json` (S3 listing: key, size, ETag, content type from `storage_objects` read in byte order (`COLLATE "C"`, S3's listing order, so the capped read matches the listed objects), `tracked`, or `tracking_unavailable` if that table can't be read; export archives excluded; capped at 100k objects → `truncated`). Each is a `sections` entry in `_metadata.json`; any failure makes the export incomplete with a warning and never writes a partial file. pg_dump's stderr is logged, not stored (it names hosts). `.github/workflows/compliance-export.yml` runs the DB-backed export suites + checks `pg_dump` in the worker image on PRs touching the export.
- **Team-tier (#663):** a project with a live `project_databases` row keeps its tenant data on the dedicated instance — the shared cluster has no schema for it (or a stale pre-upgrade copy). The export worker's `Dedicated` resolver (`dbprovider.OpenOwnerPool`, same live-row rule as `PlatformTenantContext`) reads it there **as the owner** (RLS bypass, as `eurobase_developer` on shared) in a short-lived 1-connection pool, never `PoolCache`. Live row not `active` (provisioning / restoring) → `ErrDedicatedNotReady`, the export fails and River retries; no cipher → fails. The row turns `active` at the end of an upgrade's provisioning step, *before* the data copy, so exports are also refused while `project_upgrades` has a row in `requested` / `provisioning` / `copying` / `cutting_over` (`refuseDuringUpgrade` → `ErrUpgradeInProgress`, retried; it reads `project_upgrades` on the **developer** pool — 000117 revokes the table from `eurobase_gateway`, the worker's `DBPool`). The upgrade orchestrator itself (`UpgradeProjectWorker`) runs on the developer pool too (#673) — on the gateway pool every upgrade failed at its first query and stayed in `requested`; its `Preflight` logs an error at worker startup if the pool can't read `project_upgrades` or assume `eurobase_migrator`, and `TestUpgradeWorker_ProductionRoles` runs it under the real roles in `compliance-export.yml`. **While the data copy is a stub, every upgrade fails closed** at the start (`ErrUpgradeCopyNotImplemented`, before maintenance mode or provisioning): with `TEAM_TIER_ROUTING=1` in prod, cutting over without the copy would serve the project from an empty dedicated database. Only tests set `AllowStubbedCopy`; remove the guard in the PR that implements the copy; from `live` on the dedicated database is what live traffic uses. **Never fall back to the shared cluster for a Team project.** The gateway's pre-queue `UserExistsInTenant` routes via `poolCache.GetOwner`. Exports also fail when the tenant schema doesn't exist on the source (`requireSchema`) — an empty-but-"complete" archive is what misrouting looks like.

## Storage object ownership
- SDK storage (`/v1/storage`, API key + end-user JWT) is scoped per end user by the `storage_objects` RLS policy (`is_service_role() OR uploaded_by = current_end_user_id()`): download / delete / download URLs via `assertObjectVisible`, **listings** via `visibleToCaller` (keys with a visible row only; refilled from up to `maxListPages` S3 pages), **uploads and upload URLs** via `claimKey` — a tracked key must be the caller's, an untracked key that already exists in S3 is refused, a new key is claimed (row owned by the caller) *before* anything reaches S3, so signed-URL uploads are tracked too. The tracking upsert never changes an existing owner. Upload URLs expire after at most 1 h. Console storage (key type `secret`) and edge functions are service role and unrestricted.
